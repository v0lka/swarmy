# swarmy — спецификация разработки

- **Версия:** 0.3-draft
- **Статус:** первичная спецификация, оформлена по итогам исследовательской сессии; 0.2 — открытые вопросы разрешены оператором, решения D17–D21 (§13–§14); 0.3 — введены пороги тестового покрытия (D22, §11)
- **Дата:** 2026-11-25
- **Языки:** документация — русский; код, идентификаторы, CLI, UI — английский

## 1. Обзор

### 1.1. Назначение

swarmy — расширяемая агентская система для анализа защищённости развёрнутых веб-приложений
(авторизованный пентест). Рой функциональных субагентов под управлением агента-оркестратора
исследует цель, находит недостатки и уязвимости, связывает их в деревья атак; человек-оператор
наблюдает процесс в TUI, общается с агентами и управляет ими через HITL-механизмы.

### 1.2. Целевая аудитория

Опытные пентестеры с небольшим опытом создания собственных агентов (в основном на сторонних
харнессах). Основной сценарий использования кодовой базы — **написание специализированных
субагентов-модулей**: рекогносцировка, детекторы конкретных классов уязвимостей, построение
глубоких деревьев атак из найденных уязвимостей и т.п.

### 1.3. Принципы проектирования

| # | Принцип | Следствия |
|---|---------|-----------|
| P1 | Инструмент для хакеров, не энтерпрайз-автопентестер | Каждое решение проверяется вопросом «упрощает ли это жизнь пентестеру?»; никакой RBAC, мультиарендности, «админок» |
| P2 | Расширяемость без правки движка | Модуль субагента = папка с декларативными файлами + python-инструменты; движок не меняется при добавлении модулей |
| P3 | Безопасность со старта и всегда | Цель — недоверенный источник контента (prompt injection); границы агентов — детерминированные гардрейлы, а не «надежда на промпт» |
| P4 | Просто настолько, насколько возможно, но не проще | Минимум зависимостей и абстракций; никакого `dict[str, Any]`; встроенные абстракции — только там, где есть минимум две реализации или жизненный цикл |
| P5 | Человек-в-контуре настраивается, а не выбивается | Профили строгости; интерактивный и автономный режимы оркестратора |

### 1.4. Вне скоупа v0.1 (post-MVP: §12.3 ниже; roadmap §13)

gRPC-инструменты; векторный (семантический) поиск в памяти; Docker-сандбокс исполнения;
интеграция с внешними прокси (Burp/mitm); headless-режим без TUI; движок авто-корреляции
деревьев атак; мультипользовательские режимы.

## 2. Термины и доменная модель

| Термин | Определение |
|--------|-------------|
| **Сессия (session)** | Один запуск swarmy против одной цели: конфиг скоупа, память, журнал событий, сессия чата |
| **Цель (target)** | Исследуемое веб-приложение (базовый URL + метаданные) |
| **Скоуп (scope)** | Разрешённые границы сетевой активности: домены, IP/подсети, порты, схемы |
| **Модуль субагента (agent module)** | Папка `agents/<name>/` с `AGENT.md`, опциональными `tools/`, `skills/`, `guardrails.yaml` |
| **Оркестратор (orchestrator)** | Главный deep-agent: реагирует на события, делегирует задачи субагентам, ведёт чат с оператором |
| **Событие (event)** | Типизированная запись (Pydantic-модель) в шине событий; триггер реакций оркестратора |
| **Общая память (shared memory)** | Единое хранилище фактов о цели для всех субагентов (SQLite, один файл на сессию) |
| **Находка (finding)** | Кандидат в уязвимости или подтверждённая уязвимость со статусом и severity |
| **Улики (evidence)** | Материальное подтверждение находки: файлы в сессии + типизированные метаданные; `kind` — Pydantic-enum (`http_request_response` в v0.1; `screenshot`/`har`/`grpc_file` зарезервированы, D20) |
| **Дерево атак (attack tree)** | Граф узлов-предусловий/узлов-находок с типизированными рёбрами (`requires`, `enables`, `leads_to`) |
| **Гардрейл (guardrail)** | Правило, запрещающее или эскалирующее операцию; три слоя: платформенные инварианты, базовые правила движка, модульные правила |
| **LLM-судья (judge)** | Асинхронный второй взгляд отдельной моделью на вызовы/результаты; может эскалировать в HITL, не может разблокировать детерминированный запрет |
| **HITL** | Human-in-the-loop: прерывание исполнения с запросом решения оператора (approve/reject/edit) |
| **Профиль строгости** | `paranoid` / `normal` / `yolo` — набор HITL-врат по умолчанию |

Доменная схема (упрощённо):

```
Target ─ ScopeEntry (много)
Target ─ Endpoint (много) ─ Parameter (много)
Endpoint/Parameter ─ Finding (кандидаты/подтверждения) ─ Evidence (много)
Finding ─ AttackNode ─ AttackEdge ─ AttackNode   (деревья атак)
всё  ─ Note / Fact (свободные факты с тегами)
```

## 3. Архитектура

### 3.1. Слои

```
┌────────────────────────────────────────────────────────────┐
│ L2  Интерфейс: TUI (Textual) + CLI-точка входа `swarmy`    │
├────────────────────────────────────────────────────────────┤
│ L1  Доменное ядро swarmy (наш код):                        │
│     orchestrator harness · event bus + journal ·           │
│     memory store · tool registry · guardrail pipeline ·    │
│     module loader · report generator                       │
├────────────────────────────────────────────────────────────┤
│ L0  Harness: deepagents (LangChain + LangGraph)            │
│     субагенты · HITL interrupt · skills · MCP · контекст   │
└────────────────────────────────────────────────────────────┘
```

L0 **не форкается**: используется как зависимость, расширяется документированными точками
(middleware, SubAgent-словарь, skills-пути, `interrupt_on`, `response_format`, backends).

### 3.2. Процесс и компоненты

Один Python-процесс (in-process, asyncio). Компоненты:

- **Engine** — deep-agent оркестратора (`create_deep_agent`), сконфигурированный лоадером модулей;
- **EventBus** — in-memory asyncio pub/sub + append-only журнал (таблица `events` в SQLite);
- **MemoryStore** — типизированный доступ к общей памяти (SQLite, WAL, один файл на сессию);
- **ToolRegistry** — платформенные инструменты + инструменты модулей, проверка коллизий имён;
- **GuardrailPipeline** — pre-tool-call middleware: три слоя правил + hook LLM-судьи;
- **ModuleLoader** — сканирование `agents/`, валидация манифестов, сборка SubAgent-словарей;
- **Session** — объект сессии (composition root): жизненный цикл open/resume/close, владеет всеми компонентами выше; конфиг сессии — отдельная схема `SessionConfig` (target, scope, профиль строгости, лимиты; каноника — architecture.md §2.2–§2.3).

### 3.3. Поток данных

```
субагент ──инструменты (http_*, memory_*, emit_event)──▶ GuardrailPipeline ─▶ сеть/память
   │                                                        │
   └── response_format (типизированный результат task)      ▼
                                                        EventBus ─▶ журнал (SQLite)
                                                            │
            ┌───────────────────────────────────────────────┘
            ▼
      оркестратор: политики событий → делегации task / память / вопрос оператору
            │                                          ▲
            └── результат (Pydantic) ─▶ память/TUI ────┘ (HITL-аппрувы из TUI)
```

## 4. Модуль субагента (ядро расширяемости)

### 4.1. Структура папки

```
agents/<module-name>/
├── AGENT.md          # required: YAML frontmatter + системный промпт
├── tools/            # optional: python-модули с инструментами (полная типизация)
├── skills/           # optional: контейнер скиллов по спецификации agentskills.io
└── guardrails.yaml   # optional: модульные правила гардрейлов
```

### 4.2. Фронтматтер `AGENT.md`

Поля отображаются на документированный словарь `SubAgent` deepagents:

| Поле | Тип | Обяз. | Назначение |
|------|-----|-------|------------|
| `name` | str | да | Уникальный идентификатор (имя для `task()`) |
| `description` | str | да | Что делает и когда делегировать — оркестратор решает по нему |
| `model` | str | нет | Оверрайд модели (`provider:model`), иначе модель оркестратора |
| `mode` | `isolated` \| `fork` | нет | Контекст делегации (дефолт `isolated`) |
| `interrupt_on` | map[str, bool] | нет | HITL-врата на конкретные инструменты модуля |
| `events` | list[str] | нет | Объявление типов событий, которые модуль бросает (для проверки лоадером) |
| `guardrails` | str | нет | Путь к `guardrails.yaml` (по умолчанию `./guardrails.yaml`) |

Системный промпт — тело `AGENT.md` ниже фронтматтера. `skills` и `tools` не объявляются в
фронтматтере: лоадер автоматически подключает `tools/` и `skills/` из папки модуля
(у каждого субагента — собственный изолированный `SkillsMiddleware`, как у deepagents).

### 4.3. Правила для `tools/`

- Инструмент = python-функция с **полной типизацией** аргументов и результата
  (Pydantic-модели или примитивы), docstring = описание для LLM.
- Запрещены `Any`, `dict[str, Any]`, неаннотированные параметры — проверяется линтером и лоадером.
- Зарезервированные префиксы платформенных инструментов (`memory_*`, `event_*`, `session_*`)
  модуль не может использовать в именах собственных инструментов; сами платформенные
  инструменты с этими префиксами субагентам доступны (§7.4). Коллизии имён — fail-fast
  при старте сессии.
- Сетевые инструменты модулей обязаны проходить через предоставленный платформой HTTP-клиент
  (§7) — прямые сокеты/urllib в модулях запрещены и блокируются гардрейлом-инвариантом.

### 4.4. Скиллы

Полное соответствие [спецификации agentskills.io](https://agentskills.io/specification):
`SKILL.md` (frontmatter `name` ≤64, `description` ≤1024; опционально `license`,
`compatibility`, `metadata`), ресурсы в `scripts/`, `references/`, `assets/`.
Progressive disclosure deepagents используется как есть (метаданные → инструкции → ресурсы).
Собственные инструменты скилла — через `metadata.include_tools` (расширение deepagents).

### 4.5. Загрузчик (ModuleLoader)

1. Сканирует `agents/` (пользовательские) + встроенные модули пакета.
2. Валидирует каждый манифест Pydantic-моделью `AgentModuleManifest`
   (ошибки конфигурации = fail-fast со списком проблем по всем модулям сразу).
3. Собирает SubAgent-словари: `system_prompt`, `tools` (импортированные функции),
   `model`, `mode`, `interrupt_on`, `skills=[<путь>/skills/]`,
   `middleware=[GuardrailMiddleware(правила модуля)]`,
   `response_format` — если модуль объявляет схему результата.
4. Проверяет `events` модуля против реестра типов событий.
5. Передаёт список оркестратору (`create_deep_agent(subagents=...)`).

### 4.6. Встроенные модули v0.1 (эталоны контракта)

| Модуль | Назначение | Инструменты | События на выходе |
|--------|-----------|-------------|-------------------|
| `crawler` | Первичная рекогносцировка: robots.txt, sitemap, обход ссылок, извлечение форм и параметров, карта эндпоинтов | `http_get` (+ свои парсеры), `memory_upsert_endpoint`, `emit_event` | `EndpointsDiscovered`, `EndpointUpdated` |
| `xss-detector` | Детектор отражённого XSS: постановка маркеров, контекстный анализ отражений, верификация безопасными пейлоадами | `http_get`, `http_post`, `memory_search`, `memory_save_finding`, `emit_event` | `FindingCandidate(type=xss)` |

Оба модуля написаны строго по контракту §4 (dogfooding) и служат референсом для авторов модулей.

## 5. Оркестратор и события

### 5.1. Оркестратор

Главный deep-agent с системным промптом оркестрации. Инструменты: встроенный `task`
(делегация субагентам), платформенные `memory_*`, `emit_event`, `session_info`,
`generate_report`, плюс чат с оператором (TUI). Планирование — встроенные todos deepagents.
Делегации **async-параллельные** (D19): несколько `task()` могут исполняться одновременно;
общая память и ресурсные лимиты сессии (§7.3) — глобальные для всех субагентов.

### 5.2. Таксономия событий v0.1

Единый конверт (Pydantic): `id`, `ts`, `type`, `source` (модуль/оркестратор/платформа),
`payload` (типизированный), `correlation_id` (связь с делегацией/находкой).

| Тип | Источник | Смысл |
|-----|----------|-------|
| `TargetSet`, `ScopeChanged` | платформа | Цель/скоуп сессии (изменение скоупа — только через HITL) |
| `EndpointsDiscovered`, `EndpointUpdated` | crawler и др. | Новые/обновлённые эндпоинты в памяти |
| `FindingCandidate` | детекторы | Кандидат в уязвимость (тип, endpoint_ref, evidence_ref) |
| `FindingVerified`, `FindingRejected` | верификаторы | Итог проверки кандидата |
| `AttackTreeUpdated` | строители деревьев | Мутация дерева атак |
| `GuardrailBlocked` | платформа | Сработал гардрейл (инструмент, правило, контекст) |
| `TaskRequested`, `TaskCompleted` | платформа | Служебные: делегации и результаты |
| `OperatorMessage`, `OperatorDecision` | TUI | Реплики и решения оператора |

Расширение таксономии: новый тип = Pydantic-класс + регистрация в реестре; модули объявляют
бросаемые типы в `AGENT.md`, лоадер сверяет. События создаются **только** инструментом
`emit_event` (валидация типом из реестра) или платформой — прямого доступа к шине у модулей нет.

### 5.3. Шина и журнал

- In-memory asyncio pub/sub (подписчики: оркестратор, TUI, журнал).
- Каждое событие синхронно дописывается в append-only журнал (SQLite `events`);
  журнал — первичный источник аудита сессии и восстановления (resume = журнал + чекпоинт).

### 5.4. Цикл оркестратора

1. **Реактивный контур:** политики `событие → реакция` в конфиге сессии
   (пример: `FindingCandidate(type=xss)` → делегация верификации → `FindingVerified` →
   предложение узлов дерева атак).
2. **Проактивный контур:** собственные планы оркестратора (todos) по задаче оператора.
3. **Интерактивный контур:** команды и вопросы оператора из чата.

### 5.5. Режимы автономности (переключение на лету)

| Режим | Поведение |
|-------|-----------|
| `interactive` (дефолт) | Значимые развилки (запуск тестов класса уязвимостей, верификация, изменение скоупа) подтверждаются оператором |
| `mission` | Оркестратор роет сам в пределах гардрейлов; HITL-врата и профиль строгости продолжают действовать; оператор наблюдает в TUI и может вмешаться |

### 5.6. HITL

- Механизм — `interrupt_on` deepagents + SQLite-checkpointer (состояние прерываний персистентно).
- Профили строгости задают врата по **классам инструментов**: `passive` (чтение цели),
  `network-write` (POST/PUT/DELETE к цели), `verify` (эксплуатационные проверки),
  `destructive` (потенциально ломающие операции).
  - `paranoid`: врата на всё, кроме `passive`;
  - `normal` (дефолт): врата на `verify` и `destructive`;
  - `yolo`: врата только на `destructive`.
- TUI показывает: инструмент, аргументы (санитизированные), активное правило/профиль;
  решения: approve / reject / edit.
- При параллельных делегациях (D19) запросы на аппрув выстраиваются в очередь (FIFO);
  каждое решение применяется к конкретному вызову — очередь видима в TUI (§9.2).

## 6. Общая память

### 6.1. Персистентность

Один файл на сессию: `<session-dir>/memory.sqlite` (SQLite, WAL). В `<session-dir>` же —
файлы улик и конфиг сессии; сессия = переносимая папка.

### 6.2. Сущности (Pydantic v2; таблицы зеркалят схемы)

- `Target` — базовый URL, метаданные стека (заполняется по мере исследования);
- `ScopeEntry` — домен/IP-подсеть/порт/схема;
- `Endpoint` — method, path, auth-требования, статус исследования, notes;
- `Parameter` — имя, расположение (query/body/header), тип, примеры;
- `Finding` — тип (enum: xss, sqli, auth, …), `status: candidate|verified|rejected`,
  `severity: critical|high|medium|low|info` (обязательна), `cvss_vector` (опционален),
  `endpoint_ref`, `evidence_refs`, описание;
- `Evidence` — `kind: EvidenceKind` (Pydantic-enum: `http_request_response` в v0.1;
  `screenshot`, `har`, `grpc_file` зарезервированы — добавляются без миграции схем, D20),
  путь к файлу(-ам) в сессии, метаданные (ts, инструмент);
- `AttackNode` / `AttackEdge` — узлы (предусловие/находка/цель) и типизированные рёбра
  (`requires`, `enables`, `leads_to`);
- `Note`, `Fact` — свободные записи с тегами (особенности стека, наблюдения).

### 6.3. API инструментов (доступен всем субагентам)

`memory_search` (FTS5, фильтры по типу сущности), `memory_get`, `memory_upsert_endpoint`,
`memory_save_finding`, `memory_link_attack_node`, `memory_add_fact`, `memory_add_note`.
Отдельный платформенный инструмент `update_finding_status` (без префикса `memory_*`)
переводит находку в `verified`/`rejected` и публикует `FindingVerified`/`FindingRejected` —
используется контуром верификации находок (§5.2).
Записи, указывающие вне скоупа (новые хосты в эндпоинтах), помечаются флагом `out_of_scope` —
инструменты сети их не обслуживают без расширения скоупа через HITL.

### 6.4. Поиск

- v0.1: **FTS5** — полнотекст по текстовым полям сущностей; сортировка по релевантности и типу.
- Интерфейс `SearchIndex` абстрагирует бэкенд; фаза 2: `sqlite-vec` (pre-v1, breaking changes
  возможны — пин версии) для семантического поиска; embedding-модель — из конфига LLM.

## 7. Инструментарий

### 7.1. HTTP-клиент (платформенный)

- `httpx` async-клиент в обёртке `SwarmyHttpClient`; типы `RequestSpec` / `ResponseRecord`
  (Pydantic): метод, URL, заголовки, тело, статус, время, редиректы.
- **Обязательное прохождение GuardrailPipeline** до сети (§8); запись улик (глубина настраивается);
  гигиена контекста: обрезка больших тел, детект секретов в исходящих заголовках/телах (warn).

### 7.2. Scope enforcement

- `ScopeRegistry` из конфига сессии: домены, IP/подсети, порты, схемы.
- Проверка **до** сетевого вызова; отказ вне скоупа = `GuardrailBlocked` (инвариант).
- Изменение скоупа — только `OperatorDecision` (HITL) → событие `ScopeChanged`.

### 7.3. Ресурсные лимиты (инварианты, конфигурируемые)

`rate_limit` (rps на хост), `max_concurrent_requests`, `max_body_bytes`,
`max_redirect_depth`, `total_request_budget` (на сессию), таймауты. Дефолты консервативны;
цель — предотвращение self-DoS цели (учебный кейс: исчерпание пула соединений БД).
Лимиты — **глобальные на сессию**: при async-параллельных делегациях (D19) они считаются
суммарно по всем субагентам, а не на агента — именно это удерживает рой от давления на цель.

### 7.4. Платформенные инструменты

`emit_event`, `memory_*` и `update_finding_status` (§6.3), `session_info` (скоуп, статусы,
профиль), `http_get`/`http_post`/`http_put`/`http_delete` (через платформенный HTTP-клиент,
§7.1), `generate_report` (§10). Канонический список и реестр — architecture.md §6.1.
MCP-серверы подключаются стандартно для deepagents — на уровне платформы/модуля.

### 7.5. gRPC

Фаза 2 (`grpcio`; колёса под Python 3.15 отслеживаются по grpc#41010; при отсутствии —
пин версии или сборка из исходников).

## 8. Безопасность и гардрейлы

### 8.1. Threat model самого инструмента

| Угроза | Мера |
|--------|------|
| Prompt injection из контента цели (страницы, заголовки, ответы API) | Все данные цели — недоверенный контент: цитируются как данные; системные правила запрещают исполнение инструкций из контента цели; перед входом в LLM-контекст — санитизированная проекция (§8.7): нормализация, untrusted-маркеры, обрезка |
| Утечка секретов сессии (куки, токены) | Хранение в папке сессии; маскирование в LLM-контексте и TUI (§8.7); warn при детекте секрета в исходящем |
| Несанкционированный egress | Scope-инвариант (§7.2): сетевые вызовы только в скоуп |
| Self-DoS цели | Ресурсные лимиты (§7.3) |
| Supply chain | Зависимости фиксируются lock-файлом (uv); обновления deepagents — по процедуре D18 (пин `>=0.7.41,<0.8`; ревью changelog → полный прогон тестов → bump; security-fix — внеочередной) |

### 8.2. Три слоя гардрейлов; И-композиция

Правило **любого** слоя, вернувшее запрет, запрещает операцию (композиция «по И»:
запрет = дизъюнкция запретов слоёв; разрешение требует разрешения всех слоёв).

1. **Платформенные инварианты** (неотключаемы): scope, ресурсные лимиты, egress-политика,
   запрет прямых сетевых вызовов мимо платформенного клиента.
2. **Базовые правила движка** (поставляются, отключаемы в конфиге): примеры — блок
   деструктивных SQL-конструкций (`OR 1=1`/TRUE-паттерны) в инструментах SQLi-проверок,
   блок методов `TRACE`/`CONNECT` и известных опасных пейлоадов по умолчанию.
3. **Модульные правила** (`guardrails.yaml` модуля, «собственные гардрейлы субагентов»).

### 8.3. Формат правила (`guardrails.yaml`)

```yaml
rules:
  - id: no-true-based-sqli
    applies_to: ["http_get", "http_post"]        # имена инструментов
    condition:
      any_param_matches: "(?i)('\\s*(or|and)\\s*'.*'=|1\\s*=\\s*1|true\\s*=)"  # regex по параметрам
    action: block
    severity: high
    message: "TRUE-конструкции в SQLi-проверках запрещены: риск порчи данных цели"
```

Декларативные предикаты v0.1: `any_param_matches` / `url_matches` / `header_matches` /
`body_size_above` / `tool_in`. Исполнение — детерминированный конвейер pre-tool-call
(middleware deepagents), без LLM в критическом пути запрета.

### 8.4. LLM-судья

- Асинхронный «второй взгляд» отдельной моделью (конфиг: модель + порог уверенности) на
  подозрительные вызовы и результаты; вердикт: `ok` / `escalate_hitl` / `flag`.
- **Асимметрия полномочий:** судья может эскалировать в HITL и помечать, но **не может**
  разрешить то, что заблокировано детерминированными правилами.

### 8.5. Семантика нарушения

Срабатывание (правило или эскалация судьи, подтверждённая блокировкой):
1. вызов **не выполняется**;
2. попытка фиксируется в журнале, публикуется `GuardrailBlocked`;
3. агент получает текстовый фидбек (id правила, причина) и корректирует план;
4. принудительное разрешение — только `OperatorDecision` через HITL (в обоих режимах).

### 8.6. Authorization gate

**Отсутствует** (осознанное решение: инструмент для профессионалов, ответственность на
операторе). Дисклеймер об ответственности и законности тестирования — в README и первом
сообщении чата сессии. Решение пересматривается, если появится публичная дистрибуция.

### 8.7. Санитизация LLM-контекста (граница сырых данных, D21)

Принцип: **память и файлы сессии — сырые; LLM-контекст — санитизированная проекция.**

- Улики, ответы цели и факты хранятся в сессии как есть — пентестеру нужны сырые данные
  для верификации находок и отчёта.
- Всё, что инструмент возвращает в контекст модели, проходит через `ContextProjector`:
  1. **Обрезка по байтовому бюджету** (конфигурируется по классам инструментов):
     усечение с явным маркером `[truncated N bytes]`; полное содержимое — в уликах сессии;
  2. **Маскирование секретов оператора** (куки/токены авторизации сессии): замена на
     плейсхолдер `<masked:secret-name>` в контексте и TUI; в файлах сессии — как есть;
  3. **Untrusted-маркировка**: контент цели оборачивается маркерами недоверенных данных
     (данные, не инструкции);
  4. **Нормализация** control-символов и скрытого Unicode перед входом в контекст.
- Найденные в цели секреты — данные находки: в уликах хранятся сырыми, в контекст попадают
  усечённо/замаскированно, чтобы не разносить их по истории чата и провайдерам LLM.
- Детальные правила (бюджеты по классам инструментов, паттерны секретов, формат маркеров)
  специфицируются в F2.

## 9. TUI (Textual)

### 9.1. Панели (все входят в MVP)

| Панель | Содержимое |
|--------|-----------|
| **Chat** | Диалог оператор ↔ оркестратор; переключение на живой субагент для инспекции его контекста |

| **Attack Trees** | Интерактивный рендер деревьев (раскрытие узлов, переход в находку) |
| **Progress & Plans** | Todos оркестратора, статистика сессии (прогресс по эндпоинтам/классам) |

### 9.2. Требования

- Рендер: rich-разметка (markdown, таблицы, деревья); сочетания клавиш для навигации по панелям.
- HITL-модалки модальные и неблокирующие для остального роя; при async-параллельных
  делегациях (D19) одновременные запросы встают в видимую очередь (FIFO) — решения
  применяются к конкретному вызову, статус очереди отражается в Swarm Activity.
- TUI — единственный интерфейс v0.1; headless — roadmap.
